- **Databricks:** 87 shelf-tag price changes for 11 SKUs in 3 stores and per-store sales in 4 aisles. One read-only
  query keeps the newest tag per store and SKU with `QUALIFY ROW_NUMBER() ... = 1` (the `COUNT(*)` and `LAG` windows
  in the same SELECT still see every change) and the top 2 sellers per aisle with `QUALIFY RANK() OVER (... ORDER BY
  SUM(qty) DESC) <= 2`. Local: plain Python, and the test runs the exact query in DuckDB. **33** current prices,
  **12 of 24** latest changes were cuts, P07 differs by **120 cents** across stores, and the produce tie at rank 2 is
  kept. Day 14 is the last trial day; the query is serverless and read-only, so it carries over to Free Edition.

- **Google Cloud:** 3 stores x 28 days of ice cream revenue, high temperature, promotion depth and foot traffic,
  inlined into one query that calls `ML.CORRELATION` twice (PEARSON and SPEARMAN) with `dimension_cols => ['store']`:
  24 rows (2 methods x 3 stores + overall x 3 columns). Local: pure Python, cross-checked with numpy in the test; the
  data is tie-free so Spearman needs no tie rule. Lakeside follows the weather (**r = 0.96**), Downtown the
  promotion (**0.96**), Campus foot traffic (**0.91**); pooled, temperature shows only **0.48**.

## What ran in the cloud
- Post-merge run for #52: Databricks day 14 **failed**: "Cannot resolve QUALIFY: 'sales.qty' is not present in GROUP
  BY and QUALIFY does not support aggregate functions". The top-sellers query ranked `SUM(qty)` inside `QUALIFY` in
  the same grouped SELECT, which DuckDB accepts. The latest-price `QUALIFY` was not reached separately (same
  statement). Fixed forward in PR #53: totals come from a `GROUP BY` step, then `QUALIFY RANK() OVER (... ORDER BY
  units DESC) <= 2`. Days 5-13 matched again (days 1-4 notices dropped by the 10-notice limit).
- Post-merge run for #53: Databricks day 14 **matched local** for all 33 store/SKU prices and 9 top-seller rows, so
  both `QUALIFY` forms (latest row per key, top N per group) work on the serverless warehouse; marked `ran` in #54.
  Google Cloud day 14 **failed on 3 of 24 rows**: every Pearson row and every per-store Spearman row matched to 1e-6,
  but the Spearman rollup rows (segment `[]`) did not (BigQuery 0.462 / 0.319 / 0.476 vs 0.505 / 0.334 / 0.384).
  Recomputing locally shows BigQuery ranks **within each store** and then correlates the pooled ranks (matches to
  1e-15). Not documented on the reference page. Fixed forward in #54: the local model uses that rule for the rollup
  row, and a third call without `dimension_cols` checks the all-rows Spearman. Google Cloud days 1-13 passed (day 2's
  BOOL classification hit the known internal error and the STRING fallback passed).
